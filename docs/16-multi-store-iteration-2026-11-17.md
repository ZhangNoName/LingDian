# 多店运行时、租户边界与 Review · 2026-11-17

## 问题与交付

库存初版保留了门店字段，但运行时仍仅允许主门店，多门店账号无法使用。为满足保留多租户系统的目标，本轮提供可配置的单/多店 resolver 和商家统一选店流程。当前门店是业务数据隔离边界，不引入尚无产品流程支撑的组织/品牌层级。

- `STORE_MODE=single` 默认保持主门店限制；`multi` 允许既有数据库中的多个门店并行经营。
- 两种模式都需要 `PRIMARY_STORE_ID`：公开接口不传门店时的默认入口，以及启动/readiness 的数据库检查对象。
- 平台账号管理可为商家分配多个已存在门店；商家门店列表仅返回活动会话授权的门店。
- 商家顶部统一选店，商品、订单、库存、门店信息和集成配置都使用该上下文。多店账号首次进入必须明确选择；单店账号直接进入。
- 商品、订单和收款账户接口以 `X-Store-Id` 选择一个已授权门店。多店账号省略时返回 400，越权 ID 返回 403。库存/集成继续对路径门店做授权校验。
- 门店选择按账号保存至 sessionStorage；标签页独立，退出清除，账号/授权变化时清理无效选择。存储不可用时仍可手工选店。
- 切店重建业务页面，放弃旧表单草稿和列表状态。请求重试固定原请求门店，避免切店后用新门店重试旧操作。
- 选择器和门店信息支持中英文，390px 移动布局经过浏览器检查；其他旧业务页面正文仍逐步国际化。

## 领域修正

Review 找到并修复了多店模式下的主门店残留：

1. 下单虽使用 body.storeId 查询 SKU，但营业校验原先仍读主门店；现在同一事务校验目标门店的营业与服务方式。
2. 支付意图创建和顾客支付查询原先固定主门店；现在先用 customer owner 查询订单，再使用订单所属门店选收款账户。单店模式仍收口主门店。
3. webhook 多店模式按 accountId/provider 查账户并验签，随后仍校验订单门店、账户、金额、币种及外部引用，拒绝跨店入账。
4. outbox 的待处理查询与遗留认领恢复原先只覆盖主门店；多店模式覆盖所有门店，单店模式保留原过滤。
5. 平台分类/商品建档支持明确 storeId；平台对象写操作按持久化对象的门店处理，商家操作始终传入已校验的所选 scope。
6. 顾客订单查询在多店模式下按 owner 覆盖自己的订单，不再因默认门店而隐藏本人其他门店订单。平台订单/账户读取保留全局管理语义。

## 配置与运营

模板继续默认 single，本轮未修改任何实际环境文件、数据库或生产部署。

启用 multi 前：准备已存在的稳定默认门店，执行正常数据库迁移，为商家分配明确门店范围，再部署 API 与 Web。生产 preflight 和 bootstrap 支持两个模式；multi bootstrap 仅创建本次配置的默认门店，额外授权门店必须已存在，否则事务失败，绝不把缺失门店解释为全店授权。

公开 `/stores/current` 和 `/menu/current` 支持可选 `storeId`，参数经 DTO 验证；不传时使用默认门店。现有顾客应用仍默认主门店，尚无选店、按店持久化购物车和租户入口分发。不能将后端可指定门店等同于顾客端多店闭环。

- bootstrap 回归覆盖 multi 明确授权多个已存在门店；现有单店初始化与迁移/发布测试继续执行。
- Web 回归覆盖明确选店、单店兼容、切账号/撤权、按账号恢复与不可用存储，以及切店和 401 刷新竞态时重试仍携带原门店。
- 浏览器使用拦截 API 的双店数据，验证未选店不请求业务数据、不同门店清单隔离、旧请求延迟返回、草稿清空、刷新恢复、集成/商品/订单上下文和中英文手机布局；无页面异常或 Vue 警告。
- 最终 `pnpm test`：626 项通过，1 项因缺少 Docker Compose v2 跳过；`pnpm run type-check`、`pnpm run build`、`git diff --check` 和文档链接检查通过。全量构建会清理共享包输出，因此与测试/类型检查串行，避免临时缺少声明文件造成误报。构建仍有上游工具链的非阻断警告。
- 本机未提供隔离 MySQL 或 Docker Compose；数据库级多租户并发、迁移及真实外部连接器/支付联调仍须在隔离环境验收。此轮没有执行生产迁移、上线或推送。
