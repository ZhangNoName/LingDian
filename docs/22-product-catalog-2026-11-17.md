# 商品与菜单配置迭代 · 2026-11-17

## 使用流程

将商家商品页收敛为“筛选已有商品 → 配置规格/价格 → 配置顾客选项 → 保存”。桌面使用紧凑表格，手机使用卡片；统计在手机显示三项主要数量，其余展开查看。使用现有中性色、按钮和共享 Dialog，不添加装饰性图表或新 UI 库。

页面、配置、类型/状态、校验和错误提供简体中文/英文；CNY 金额按语言格式化。商品名、分类、商家填写内容保持原文，不自动翻译业务数据。语言与其他商家页面共用设置。

筛选与详情由 URL 的 keyword/type/page/pageSize/productId 表达，支持刷新和返回；无效参数归一化，越界页码回到有效范围。未应用的筛选明确提示并禁用翻页/刷新。统计覆盖当前门店全部商品，不冒充筛选汇总。切换门店清理旧商品详情，请求序列和页面卸载使迟到响应失效。

配置使用原生表单，分为规格/价格和顾客选项两个页签；提交时同时校验隐藏页签。价格至多两位小数，参考数量为非负整数，名称和列表规模与 API 限制对应。保存中禁用编辑、重复提交及关闭，失败保留草稿。冲突提示关闭后重新读取，不能直接覆盖最新版本。

新增规格使用临时 ID，可以在同一次保存中绑定其选择组或引用。移除仍被表单选项引用的规格时先要求解除引用。默认规格归一化为一个启用规格；全停用配置允许保存，列表明确提示顾客菜单不展示。

“参考数量”明确为维护记录；实际原料库存、订单预占/扣减/释放和预警仍由销售配方、原料台账负责。新建商品、图片、上下架和发布仍依赖平台管理，本轮没有宣称完成商家建档发布闭环。

## 一致性与审计

新增 products.configurationVersion（默认 0）。商家完整配置、单独价格和参考数量修改必须带 expected_version；先验证 merchant/store scope，再校验版本。事务按商品版本条件更新，冲突返回 catalog.stale；随后按 ID 排序锁定该商品既有 SKU，更新配置、刷新父商品汇总并写入身份审计，审计失败整个事务回滚。

保留 SKU 身份；移除规格仅停用，已有原料配方与历史订单不删除。配置不修改 recipeVersion 或已下单快照。选择组被其他商品使用时复制组和选项再绑定当前商品，避免修改波及其他商品。引用 SKU 必须属于同一门店；绑定指定规格必须属于当前商品，外来规格 ID 不能被用于修改其他商品。

平台旧接口保持可省略版本，每次写入仍递增配置版本，防止商家旧草稿覆盖平台更新。平台基础价格/数量更新在事务内读取当前活动默认规格，避免使用加锁前的旧默认规格。平台旧调用自身仍没有强制乐观锁；商家 UI 遇到不返回版本的旧 API 会禁止保存。

本轮审计记录商品配置/规格摘要或 SKU 修改前后价格与数量，不提供完整配置历史还原、撤销或独立审计产品页。列表/统计和保存后详情是独立读取，不能描述为同一个原子快照。

## 部署与验证

新增迁移 20261117_variant_configuration_versions；先通过安全迁移入口部署，再同步更新 API 与商家 Web。旧商家客户端无版本写入会被拒绝，平台兼容路径保持可用。没有连接业务数据库或修改本地环境凭证。

- 临时 MySQL 8.4.13 完整重放 17 个迁移，迁移历史与 schema 均无漂移。
- 使用生产服务验证并发配置仅成功一次、过期配置/单独改价拒绝、跨店拒绝、保留配方、共享组复制、新规格 ID 绑定及审计失败回滚；原有订单库存、报表、预警和占用核验继续验证。
- 单元测试覆盖版本认领、商家鉴权先于版本验证、金额/名称/数量/规模限制、默认规格归一化、独立草稿及 URL 筛选编码。
- 浏览器使用双店合成 API 数据验证中英文、390px 卡片/配置、筛选刷新恢复、新规格绑定、金额提交、冲突保留草稿、保存锁、空状态、切店和加载失败；此项不代替生产环境端到端验收。

`pnpm test`：692 项通过，1 项因缺少 Docker Compose v2 跳过；全仓 `pnpm run type-check`、`pnpm run build` 通过。最终 Web URL 参数收紧后，前端 102 项测试、类型与构建再次通过。构建保留既有上游工具链的非阻断警告。文档链接和差异空白检查随全仓验收执行；临时 MySQL/Web 进程与数据库运行目录在验收后清理。
