# LingDian 权限、安全与能力缺口分析

> 审查基线：2026-08-29 当前工作区。本文用于研发排期和上线门禁，不替代安全渗透测试、支付渠道验收或正式法律审查。结构现状见 [系统结构](./11-system-structure.md)，逐模块现状见 [模块目录](./12-module-catalog.md)。

## 1. 审查结论

当前权限模型已经具备三个正确基础：

1. 顾客、商家、平台管理员使用不同 token audience；
2. 顾客地址/订单按用户归属过滤，商家商品/订单/集成按服务端签发的门店范围过滤；
3. 管理账号存在层级约束，密码、角色、状态或门店范围变化会撤销会话。

但它仍是“固定角色 + 少量资源范围”，不是完整 RBAC/ABAC。当前最严重问题不只是缺少权限配置页面，而是支付与会话实现中存在可导致越权、旧令牌复活、重复扣款或订单/资金状态不一致的路径。

综合判断：

- **演示/MVP**：认证、菜单、基础下单、商家商品/订单查询可以继续使用；
- **单店现金试点**：在明确不接在线支付、不承诺强库存、隐藏占位模块并补齐门店规则后可做受控验收；
- **单店在线交易生产**：仍须先关闭会话、支付、规格、迁移和正式发布信息相关 P0；
- **稳定单店经营**：还需要 P1 的营业设置、履约、可观测性、迁移和运营处置能力；员工权限是否前置取决于是否有多人使用商家端。

## 2. 风险分级

| 等级 | 定义 | 处理要求 |
| --- | --- | --- |
| **P0 阻塞** | 可能造成未授权访问、错误扣款/退款、交易事实不一致、下错门店/商品，或发布信息明确未完成 | 对应使用场景上线前必须关闭 |
| **P1 核心** | 不一定立即造成资金/安全事故，但会阻断稳定营业、重复部署、人工处置或最小权限 | 生产试点前完成，或有书面降级边界和补偿方案 |
| **P2 增长** | 影响规模经营、效率、数据决策和可维护性 | 核心闭环稳定后按业务优先级建设 |
| **P3 治理** | 命名、重复实现、文档和体验一致性问题 | 持续清理，避免形成长期债务 |

## 3. 当前身份与权限模型

### 3.1 身份域

| 身份 | Token audience | 固定角色 | 当前数据范围 | 主要客户端 |
| --- | --- | --- | --- | --- |
| 顾客 | `user-api` | `USER` | 自己的用户 ID | `uniapp/` |
| 商家 | `merchant-api` | `MERCHANT` | 固定包含唯一生产门店的 `merchantStoreIds` | `web/` |
| 平台管理员 | `admin-api` | `ADMIN` | 当前通常为平台全局 | `admin/` |
| 超级管理员 | `admin-api` | `SUPER_ADMIN` | 平台全局 + 超管专属动作 | `admin/` |
| Connector | HMAC 服务身份 | 无用户角色 | 指定收款账户/事件 | 独立连接器 |

`AccessTokenGuard` 负责 token、session、用户状态和 sessionVersion；随后由 `UserApiGuard`、`MerchantGuard`、`AdminGuard` 或 `SuperAdminGuard` 做 audience/角色收窄。对象归属和门店范围主要在 service 查询条件中执行。

### 3.2 当前资源矩阵

| 资源/动作 | 顾客 | 商家 | ADMIN | SUPER_ADMIN | 现状评价 |
| --- | --- | --- | --- | --- | --- |
| 公开门店/菜单 | 公开读 | 公开读 | 公开读 | 公开读 | 已由服务端精确解析 `PRIMARY_STORE_ID`，不再依赖最早记录 |
| 自己的地址 | 读/删/默认/导入 | — | — | — | 用户归属已执行 |
| 自己的订单 | 创建、列表、详情 | — | 全局读/改状态/软删 | 全局读/改状态/软删 | 顾客归属已执行；平台动作过宽 |
| 授权门店订单 | — | 读、改状态、软删 | 全局 | 全局 | 门店范围已执行；无岗位/动作权限 |
| 授权门店商品 | — | 读、配置、改库存/价格 | 全局 CRUD/状态/图片/配置 | 全局 | 门店范围已执行；商家无法完整建档；平台授权过粗 |
| 门店集成开关 | — | 授权门店读写 | — | — | 门店范围已执行；无敏感动作权限与审计 |
| 自己订单的支付 | 创建意图、查询 | 门店账户只读 | 全部账户只读 | 账户写 + 全部只读 | 归属与主门店校验已覆盖幂等/冲突恢复路径；并发资金一致性仍待关闭 |
| 平台账号 | — | — | 受层级约束管理更低角色 | 管理更低角色 | 服务端层级有效；前端未正确表达动作能力 |
| 系统错误日志 | — | — | — | 读 | 前后端一致 |

代码入口：`backend/src/common/auth/`、`backend/src/modules/*/*.controller.ts` 和各 service 的查询条件。

### 3.3 已做得较好的安全边界

- 管理、商家、顾客 token 不能跨 audience 直接复用；
- access token 不是只验签，还查数据库 session 与账号状态；
- 顾客订单、地址及支付查询使用当前用户归属；
- 商家商品、订单、集成与支付账户使用服务端 claims 中的门店 ID；
- 账号停用、密码和门店范围变更可递增 sessionVersion/撤销 session；
- 订单提交重新读取 SKU、选择项与价格，客户端金额不是交易事实；
- webhook 验证原始请求签名，并核对账户、金额、币种、外部意图与事件 ID；
- 商品图片检查 MIME、文件签名、大小并做服务端转码；
- 日志入口有来源/audience 校验、大小限制和基础脱敏。

这些能力应保留，并补足下面的原子性和策略层，而不是替换成只在前端隐藏按钮的“权限”。

本轮静态遍历没有发现私有业务 Controller 明显漏挂 Guard；但应用没有“全局默认认证 + 显式 `@Public()`”机制，路由是否公开仍依赖开发者逐个添加 Guard，后续新增接口存在 fail-open 风险。

## 4. P0：上线阻塞项

### P0-SEC-01：注销后的旧 access token 会在同设备重新登录后复活

**证据**：`backend/src/modules/auth/session.service.ts` 的 `create()` 以 `(userId, audience, device)` upsert session。注销把该行改成 `REVOKED`，重新登录又把同一行和同一 session ID 改回 `ACTIVE`，且普通注销不递增用户 sessionVersion。

**影响**：注销时已失效的旧 access token 仍携带相同 `sid` 和 `sv`；用户在同设备标识重新登录后，该旧 token 在自身过期时间内可能再次通过服务端 session 校验。若令牌曾被复制，注销不能持续切断它。

**修复原则**：每次登录创建新的不可复用 session ID，或引入不可回退的 session generation/issued-after 校验；不能用“重新激活同一 session 行”作为登录。增加“注销 → 同设备重新登录 → 旧 token 仍为 401”的回归测试。

**关闭条件**：单设备注销、全端注销、密码修改、重登录和 refresh replay 的旧 token 矩阵测试全部通过。

### P0-PAY-01：PaymentIntent 幂等命中存在对象级越权 — 已关闭（2026-08-29）

此前 `createIntent()` 先按 `(orderId, clientRequestId)` 返回已有意图，再验证订单归属，未授权调用者可能借幂等快捷路径取得其他顾客的支付意图。

现在服务先按 `orderId + customerUserId + PRIMARY_STORE_ID + isDeleted=false` 读取已授权订单；订单不存在、属于其他顾客、属于其他门店或已软删时统一返回未找到，且不会查询 PaymentIntent。只有授权成功后才处理已有幂等结果、活动支付冲突和创建流程。

唯一约束冲突的恢复查询也位于同一次订单授权之后，不能绕过 owner/store scope。回归测试锁定“未授权订单不会进入幂等查询”，并覆盖合法幂等返回与唯一冲突恢复分支；后续增加缓存或重试快捷路径时必须保持同样顺序。

### P0-PAY-02：同一订单可并发创建多个活动支付意图

**证据**：服务先 `findFirst` 检查活动意图，再 `create`；数据库只唯一约束 `(orderId, clientRequestId)`，不同幂等键不会冲突。检查与创建不在带订单锁/条件占位的同一事务中。

**影响**：两个并发请求可以分别通过检查并调用 Connector，产生多个可支付意图，最坏会重复扣款。另外，用于把订单支付渠道写入订单的条件 `updateMany()` 没有检查影响行数；若订单在前一次读取后被取消，代码仍可能继续向渠道发起支付。应用层先查后写不能充当并发不变量。

**修复原则**：在数据库中表达“一个订单最多一个活动支付尝试”，例如订单级活动支付占位/版本条件更新，或终态时清空的唯一 active key；创建意图、占位和 Connector 调用需有明确事务/补偿边界。不要只增加一次 `findFirst`。

**关闭条件**：真实数据库并发测试证明不同幂等键只有一个请求能获得活动意图；订单取消与创建支付竞态只能有一个胜者；失败、过期后可安全重试。

### P0-PAY-03：Connector 同步成功会造成支付成功、订单未支付

**证据**：Connector `createIntent()` 返回 `SUCCEEDED` 时，当前代码只把 PaymentIntent 更新为成功，没有创建交易流水或推进订单；之后成功 webhook 看到 intent 已是 `SUCCEEDED` 会提前把事件标记完成并返回。

**影响**：资金已经成功，但订单可能永久停在 `PENDING_PAYMENT`，交易流水也缺失；人工无法仅凭订单判断真实资金状态。

**修复原则**：同步结果和 webhook 必须调用同一个幂等的“确认支付”领域操作，在一个事务中写 PaymentIntent、PaymentTransaction、Order 与 OrderStatusLog。重复确认应补齐缺失派生状态，不能仅按 intent 终态提前返回。外部调用成功但本地写失败时必须通过主动查单/Saga 补偿，不能把已有 `CREATED`/`FAILED` 意图直接当作安全重试结果。

**关闭条件**：同步成功、先 webhook 后同步、重复 webhook、事务中断后重放和晚到支付五类集成测试均能收敛到相同事实。

### P0-PAY-04：在线退款没有资金事实闭环

**证据**：订单状态机允许多个已支付/履约状态直接转入 `REFUNDED`；当前支付模块没有退款 API、退款意图、渠道调用和退款回调。

**影响**：界面可以显示“已退款”，但渠道资金未退，形成直接财务与客诉风险。

**修复原则**：在线支付订单只能由成功的 RefundTransaction 推进退款金额与订单退款状态；商家操作应创建退款请求，而不是直接写终态。现金订单可走经审计的线下退款流程，两者必须分开。

**关闭条件**：全额/部分退款策略明确，渠道退款、回调、重试、重复事件、失败和人工差错流程可验证；在此之前禁用在线订单的 `REFUNDED` 动作。

### P0-PAY-05：顾客端尚未接真实支付

当前结算固定提交 `paymentChannel: cash`，页面和订单详情显示“模拟支付”，没有创建 PaymentIntent、调起微信/支付宝等 SDK、服务端结果查询或失败恢复。

若首期只做现金试点，应在环境配置中彻底关闭在线渠道并清晰标识；若上线在线收款，则必须在关闭 P0-PAY-02～04 后完成真实沙箱/生产商户端到端验收，且客户端只能显示服务端确认结果。

### P0-PAY-06：在途支付引用可变收款账户

PaymentIntent 只引用当前 `PaymentAccount` 行；超管可原地修改 `externalAccountId` 与 `connectorConfigKey`。旧意图回调到达后会用修改后的账户标识和密钥验签/匹配，可能无法确认已发生的付款。账户变更也没有 actor 审计、审批或密钥轮换窗口。

修复原则：收款账户配置版本不可变，PaymentIntent 固定引用创建时版本；轮换以新版本生效并为旧版本保留有限回调验证窗口。敏感变更需要 step-up、maker-checker 或至少强审计。

### P0-PAY-07：支付/订单超时与迟到支付没有收敛策略

PaymentIntent 有 `expiresAt`，但没有过期 worker；`PENDING/PROCESSING` 会一直阻塞新尝试。Webhook 也没有按过期/已关闭订单形成统一的迟到支付处置，当前只要订单仍待支付就可能记作正常匹配。

关闭条件：定义订单/意图双超时、渠道关单前置、主动查单、迟到支付自动退款或人工差错路径，并验证乱序、停机恢复和重复任务幂等。

### P0-CAT-01：消费者规格选择与服务端商品模型不一致

当前顾客端只取默认 SKU，每个选择组近似单选，并忽略 `MULTIPLE`、min/max、可选组和 SKU 级作用域。服务端虽会拒绝非法组合，但客户端可能给出错误价格、错误默认选择或让合法商品无法下单。

关闭条件：SKU 维度选择、商品/SKU 组作用域、单选/多选、必选/可选、min/max、引用 SKU 数量与服务端契约一致，并用契约用例覆盖。

### P0-STORE-01：单店模式没有成为系统不变量 — 已关闭（2026-08-29）

产品明确只运营一个店铺，因此顾客端不需要选店、地理位置或跨店购物车。此前公开门店与 `/menu/current` 自动取数据库最早创建门店，顾客提交的 `storeId` 也参与决定下单门店。

现在服务端以 `StoreContextResolver` 精确解析 `PRIMARY_STORE_ID`：当前门店、菜单、商品、订单、支付账户和商家范围均固定到主门店；下单 `storeId` 可省略，相同值兼容、不同值拒绝；匿名 GET 不再写库。`Store` 与各表的 `storeId`、商家 scope 数组继续保留，未增加“数据库只能有一条 Store”的约束。

生产环境必填 `STORE_MODE=single` 与 `PRIMARY_STORE_ID`；启动/readiness 只校验数据库可达和主门店存在，`CLOSED`/`RESTING` 不视为宕机，下单再按 `OPEN` 与服务方式开关拒绝。demo seed 使用确定性主门店 ID，发布候选与容器健康检查使用 `/api/health/ready`。

### P0-REL-01：空库迁移不可复现

现有 Prisma 迁移从认证增量开始，业务核心的门店、分类、商品、SKU、订单等基础表没有初始 migration；后续迁移直接假设这些表存在。新环境、灾备恢复或 CI 空库无法仅靠 `prisma migrate deploy` 重建完整 schema。

关闭条件：建立经过现有生产数据兼容评审的 baseline；在临时 MariaDB 从空库执行全部迁移，再运行 schema drift 检查与核心读写 smoke test。不要通过删除生产迁移历史处理。

### P0-REL-02：生产发布缺少仓库内可验证的人工门禁与恢复证明

`.github/workflows/deploy.yml` 在 push `main` 后通过验证即进入生产 SSH 部署，没有声明 GitHub production environment 审批；发布脚本先执行数据库迁移，仓库内也没有自动备份及恢复验证。外部是否配置分支保护无法从代码确认，因此不能把它当作已有控制。

关闭条件：确认并固化受保护分支/审批人、production environment、迁移预检、兼容性策略和可恢复备份证明。若坚持全自动发布，也必须有同等强度的变更审批、渐进发布与自动停止/补偿机制。

### P0-COM-01：正式发布信息仍是显式占位

`uniapp/src/legal/legal-documents.ts` 仍包含运营主体、联系方式、投诉/注销渠道、第三方服务商、数据保存期限与存储地点等多处 `【正式发布前补充】`，且产品没有自助注销入口。

关闭条件：由实际运营方和专业法律/隐私人员确认真实信息、处理活动与留存/删除能力，完成正式审核和版本发布；研发不能猜测填入主体或服务商信息。

### P0-INV-01：限量/强库存承诺下没有防超卖能力（条件阻塞）

当前下单不检查、预占或扣减库存，页面还明确提示“库存暂不阻断下单”。如果首期商品不限量或采用人工售罄，可作为明确降级；只要产品对外承诺库存数量、限量商品或售罄强一致，就必须在上线前实现预占—支付确认—取消/超时释放及并发测试。

## 5. P1：生产试点核心缺口

| 编号 | 缺口 | 风险/影响 | 最小关闭条件 |
| --- | --- | --- | --- |
| P1-IAM-01 | 商家员工、岗位和动作权限缺失 | 任一商家账号能改价格、库存、订单和集成开关 | 多人使用商家端前完成员工、角色、动作权限；门店 scope 固定为唯一门店 |
| P1-IAM-02 | 平台商品与订单只用宽 `AdminGuard` | 普通 ADMIN 拥有全局交易和商品写能力 | 拆成显式权限点；默认拒绝；敏感动作审计 |
| P1-IAM-03 | admin 前端权限与后端层级不一致 | 普通 ADMIN 可见“新建管理员”，提交必然 403；`users:write` 未用于动作 | 服务端返回 capabilities 或前端按相同策略禁用/解释 |
| P1-IAM-04 | 无全局默认拒绝授权 | 新 Controller 漏写 Guard 就会公开 | 全局认证/策略 Guard，公开路由必须显式 `@Public()`；加入路由枚举测试 |
| P1-IAM-05 | 内部 service 的 scope 可省略并退化为全局 | 新调用点漏传 scope 会绕过唯一门店边界 | 强制 `RequestScope`；平台全局 repository 使用显式不同接口 |
| P1-IAM-06 | 两套商家账号治理策略冲突 | `/admin/merchants` 仅超管，`/admin/users` 又允许 ADMIN 管理 MERCHANT | 确定唯一产品策略并统一 API、UI、测试与审计 |
| P1-IAM-07 | `user-api` audience 与 `USER` 角色语义不一致 | UserApiGuard 不要求 USER；移除角色不一定撤销顾客能力 | 明确 audience 是否就是能力；按结论统一签发、Guard 与撤权测试 |
| P1-STORE-01 | 唯一门店设置写能力缺失 | 当前门店页已读取真实主门店，但不能维护经营条件 | 增加资料、营业时段、服务方式、配送范围编辑和审计；桌台/二维码按堂食需求建设 |
| P1-ORDER-01 | 已关闭：下单执行门店状态和服务方式开关 | 服务端拒绝已关闭或禁用的堂食/配送/自取 | 保持三类服务方式回归测试 |
| P1-ORDER-02 | 无未支付超时、客户取消和自动关单 | 僵尸订单、活动支付和库存无法释放 | 独立 worker、幂等关单、支付查单前置、可观测重试 |
| P1-ORDER-03 | 履约状态未独立建模 | 状态按钮不能表达接单、备餐、出餐、核销/配送 | 最小履约单/事件、商家实时工作台与顾客状态同步 |
| P1-CAT-01 | 商家无完整商品建档发布入口 | 商品只能靠脚本/API 初始化 | 分类、商品、图片、SKU、选项、上下架、菜单发布闭环 |
| P1-PAY-01 | 无主动查单、超时关闭、日终对账和差错单 | 丢 webhook 或晚到支付无法自动收敛 | worker + 对账结果 + 人工处置队列 + 告警 |
| P1-PAY-02 | 渠道交易号没有账户/提供方级全局唯一 | 不同 intent 可能重复记录同一外部成功交易 | 建立 provider/account/transaction ID 唯一不变量与并发测试 |
| P1-OPS-01 | outbox 无死信 UI/重放和任务告警 | 外部 POS/打印失败只能查库处理 | 查询、重放/跳过、权限、审计、积压与死信告警 |
| P1-AUD-01 | 敏感业务变更无统一审计 | 无法追责价格、库存、支付账户、集成变更 | actor/action/resource/before/after/requestId 审计模型与查询 |
| P1-OBS-01 | 无 request/trace ID、指标和告警 | 跨端/支付/连接器故障难定位 | 全链路 ID、核心 RED/交易指标、SLO 和告警 |
| P1-OPS-02 | 部分关闭：已分离 liveness/readiness 并校验数据库主门店 | 尚未检查迁移漂移、磁盘和其他关键依赖 | 增加依赖分级、指标与告警 |
| P1-TEST-01 | 无真实数据库 E2E 与并发交易测试 | ORM、约束、事务和迁移问题无法在 CI 发现 | 临时 MariaDB、迁移、auth/order/payment 并发与回调测试 |
| P1-DATA-01 | 会话、验证码、OAuth、outbox 等生命周期不完整 | 安全数据和 PII 长期累积 | 每类数据留存表、清理 worker、legal hold 与可观测结果 |
| P1-UX-01 | 生产导航展示静态经营数据 | 商家误把 mock 当真实指标 | 隐藏/feature flag 所有占位一级模块 |
| P1-ACC-01 | web/uniapp 无显式退出，顾客无注销/解绑 | 用户无法正常结束会话或行使账号操作 | 退出入口、全端退出、注销/解绑流程及风险提示 |
| P1-SEC-01 | 管理员/支付配置无 MFA 或 step-up | 单一密码会话可执行高风险配置 | 管理员 MFA；支付账户、权限、退款等敏感动作二次验证/审批 |
| P1-SEC-02 | 验证码错误无目标级失败计数/锁定 | 主要依赖进程内 IP 限流，手机号/账号可被分布式尝试 | 目标/IP/设备多维计数、短期锁定、分布式存储和告警 |
| P1-PRIV-01 | 订单、地址、认证审计和 outbox PII 缺留存/匿名化 | 软删后长期保存和外发个人信息 | 数据分级、最小字段、加密、留存/删除任务与 legal hold |
| P1-PRIV-02 | 普通 ADMIN 可读全平台账号与手机号 | 超管/顾客敏感身份没有字段级或对象级读隔离 | 拆 `users:read` / `users:read_sensitive`，按职责最小化投影 |
| P1-DATA-02 | 跨表同店不变量主要靠 service | 内部脚本可能把商品、订单和支付账户关联到非生产门店 | 所有写入校验 `PRIMARY_STORE_ID`；可行处增加复合唯一键/外键与一致性测试 |
| P1-REL-01 | 多目标发布不是原子切换 | 新前端可能与旧 API 长时间组合 | 先准备全部候选；记录全组旧版本；任一步失败整组补偿回滚 |
| P1-REL-02 | 无发布后公网冒烟 | 容器本机健康不代表 HTTPS、CORS、深链和上传正常 | 自动检查四个公网入口、登录刷新、只读业务 API 与上传读取 |
| P1-CI-01 | CI 无 `pull_request` 触发 | 问题到 main/部署前才发现 | 增加 PR verify，生产 deploy 与 verify 工作流解耦 |

如果商家端长期只有店主本人使用，P1-IAM-01 可以后移，但必须保持独立个人账号，不能多人共享一个商家账号。一旦店员、收银、后厨或财务开始登录系统，动作级权限应在发放账号前完成。

## 8. 目标权限模型

### 8.1 模型

建议采用“RBAC 赋能力 + 数据范围/对象关系约束”的组合，而不是只增加更多角色枚举。

```text
Subject（用户/服务账号）
  ├─ PlatformRoleAssignment（平台治理）
  └─ StoreMembership（唯一生产门店的员工身份）
       └─ RoleAssignment
            ├─ Role（可配置角色）
            └─ Permission（resource:action）

Policy check = audience + active subject + permission + primary store/owner relation + domain invariant
```

建议核心实体：

- `Store`：保留现有门店实体，并由 `PRIMARY_STORE_ID` 指定唯一生产门店；
- `StoreMembership`：用户在该门店的员工身份与状态；
- `Role`、`Permission`、`RolePermission`；
- `RoleAssignment`：员工获得的动作权限角色；
- `AuditEvent`：授权和敏感业务动作记录。

顾客“只能看自己的订单”属于对象关系，不应建成可分配角色。平台超管也不应绕过金额、退款、订单状态等领域不变量。

### 8.2 权限命名

统一使用 `resource:action`，数据范围另存，不把门店 ID 拼进权限名。例如：

```text
stores:read            stores:update
catalog:read           catalog:write        catalog:publish
prices:write           inventory:adjust
orders:read            orders:accept        orders:fulfill
orders:cancel          refunds:request       refunds:approve
payments:read          reconciliation:manage
integrations:read      integrations:manage
members:read           promotions:manage
staff:read             staff:manage          roles:manage
audit:read             system_logs:read
```

敏感能力要拆分，例如 `catalog:write` 不自动包含 `prices:write`，`orders:fulfill` 不自动包含 `refunds:approve`。

### 8.3 建议角色模板

| 角色模板 | 默认范围 | 典型能力 | 明确不包含 |
| --- | --- | --- | --- |
| 平台超级管理员 | PLATFORM | 平台配置、账号/角色治理、支付账户治理 | 不能绕过交易不变量 |
| 平台运营 | PLATFORM | 门店、商品与订单只读/有限处置 | 密钥、超管、任意退款 |
| 安全审计员 | PLATFORM | 审计/日志只读、会话处置 | 商品、订单、资金写 |
| 商户所有者 | STORE | 员工、门店设置和经营模块 | 平台配置、支付密钥明文 |
| 店长 | STORE | 门店设置、商品、订单、员工排班/有限退款 | 平台配置、支付密钥 |
| 收银员 | STORE | 订单、收款、经授权取消 | 价格、角色、结算配置 |
| 后厨 | STORE | 接单、制作、出餐 | 顾客敏感信息、价格、退款 |
| 仓管 | STORE/WAREHOUSE | 库存、盘点、采购 | 订单退款、员工权限 |
| 财务 | STORE | 支付流水、退款审核、对账、导出 | 商品和员工管理 |
| 营销运营 | STORE | 会员分群、券和活动 | 支付账户与结算 |

模板只提供默认值，实际授权仍需可审计，并限制谁可以授予与自己同级或更高的能力。

### 8.4 服务端授权顺序

每个受保护用例按固定顺序执行：

1. 校验 access token、session、账号状态和 audience；
2. 解析所需 `resource:action`；
3. 解析唯一生产门店，并计算用户在该门店的动作权限；
4. **带 scope/owner 条件查询对象**，未授权时不先返回缓存或幂等结果；
5. 执行订单、支付、库存等领域不变量；
6. 在同一事务中写业务事实和必要审计；
7. 返回服务端计算的 `allowed_actions` 供前端改善体验。

Controller guard 解决“能否进入用例”，service/repository 解决“能否访问这个对象”。两层缺一不可。

## 9. 推荐的后端策略接口

不要求立即引入复杂策略引擎，可先统一一个轻量接口：

```ts
type Permission =
  | 'orders:read'
  | 'orders:fulfill'
  | 'refunds:approve'
  | 'prices:write'
  | 'inventory:adjust';

type DataScope = {
  primaryStoreId: string;
  ownUserId?: string;
};

authorize(user, permission): DataScope;
```

Repository 查询必须接收 `DataScope` 并合并到 SQL 条件；禁止 controller 收到 `storeId` 后仅用 `includes()` 作为唯一授权，也禁止先全局查询对象再在响应层过滤。

## 10. 业务审计最小模型

以下动作至少写不可变审计事件：

- 登录、注销、刷新重放、密码/身份/会话变化；
- 账号、员工、角色、权限和门店范围变化；
- 商品发布、价格、库存调整；
- 订单取消、状态人工处置；
- 支付账户、支付查单、退款和对账差错处理；
- 集成开关、死信重放/跳过；
- 数据导出、账号注销与隐私请求。

建议字段：`actorUserId`、`actorAudience`、`action`、`resourceType`、`resourceId`、`storeId`、`before`、`after`、`reason`、`requestId`、`ip`、`device`、`createdAt`。敏感值应做白名单快照/哈希，不能把密码、token、密钥或完整支付载荷写入审计。

## 11. 分阶段落地路线

### Gate 0：安全与交易事实

- 修复 P0-SEC-01、P0-PAY-02～04，并增加真实数据库并发/回调测试；
- 决定首期现金或在线渠道，禁止“模拟支付”混入生产；
- 修正规格选择；固化唯一生产门店；明确库存承诺；
- 建立可重复迁移 baseline；完成运营与法律信息核验。

**退出标准**：不存在旧令牌复活、对象越权、重复活动支付、资金/订单分叉和假退款；空库可重建。

### Gate 1：可控生产试点

- `PRIMARY_STORE_ID`、单店设置与营业/服务方式服务端校验；
- 商品建档发布、订单超时/取消、最小履约工作台；
- 商家员工与首批岗位权限；
- 主动查单/对账、死信处置、业务审计、readiness 与核心告警；
- 隐藏所有静态经营模块。

**退出标准**：一笔订单从选品、下单、收款、履约到取消/退款均可闭环，异常有可观测的自动或人工处置路径。

### Gate 2：经营效率

- 库存/采购、会员/券、财务结算、通知；
- 指标口径与分析；
- 设备/打印/配送的双向事件；
- 对象存储、备份恢复演练和多副本任务模型。

### Gate 3：单店规模与可靠性

- 大规模数据归档、数据仓库、SLO/容量治理；
- 达到独立扩缩容或团队边界后再评估拆服务。

组织/品牌、多门店和跨店能力不属于当前路线；只有经营策略正式变化时才重新评估。

## 12. 验收清单

上线评审不再以“接口已写/页面能打开”为完成标准。每个核心模块至少回答：

- 是否有唯一的服务端事实和状态机？
- 是否对 duplicate、retry、并发、超时和晚到事件收敛？
- 是否在所有快捷路径执行 owner/scope 授权？
- 是否有真实数据库/Connector 契约/E2E 测试？
- 是否记录敏感动作审计，且不记录秘密？
- 是否有指标、告警、人工处置和补偿？
- 是否定义 PII 最小化、留存、删除和导出？
- 是否完成目标环境、真实商户和灾备恢复验收？

任何一项回答“不知道”，都应作为显式风险进入发布决策，而不是由静态页面或 happy-path 单元测试代替。
