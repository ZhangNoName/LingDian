# 小程序用户协议与隐私政策确认设计

## 背景

当前小程序登录页提供手机号验证码登录和微信手机号快捷登录，但没有展示用户协议、隐私政策或用户同意记录。登录页视觉上也存在品牌红与微信绿争夺主视觉、表单卡片偏厚、内容组偏重等问题。

本次设计在不改变现有认证业务语义的前提下，增加两份可阅读的协议、登录前的明确同意动作、协议版本校验和服务端同意记录，并同步收敛登录页的视觉层级。

## 目标

1. 提供可在小程序内打开和滚动阅读的《用户服务协议》和《隐私政策》。
2. 用户未勾选协议时，不允许获取验证码、发起第三方登录或完成任何用户登录。
3. 服务端只接受当前有效的协议版本，并记录用户同意的协议类型、版本、时间、IP 和设备标识。
4. 对微信快捷登录、手机号验证码登录、第三方账号绑定手机号三条用户登录路径使用一致的同意规则。
5. 登录页使用零点点餐品牌红建立单一主视觉，微信入口降级为辅助操作，表单在常见手机高度下更轻、更紧凑。
6. 协议内容是可审阅的业务初稿；运营主体、注册地址、联系方式、投诉渠道、实际第三方服务商等运营信息必须在正式发布前补齐。

## 非目标

- 本次不新增协议后台编辑器或远程 CMS。
- 本次不改变商品、订单、支付、配送、退款或认证令牌的业务规则。
- 本次不把微信开发者工具的隐私弹窗伪装成自有协议同意；微信平台隐私指引仍需在小程序后台单独配置。
- 本次生成的协议不替代运营方的法律审核、主体信息核验或上线前合规备案。

## 方案选择

### 方案 A：本地协议页面 + 服务端版本校验和同意记录（采用）

协议文本随小程序发布，页面离线可读；登录请求携带协议版本，服务端校验版本后记录同意。协议更新时随小程序版本更新，旧版本的同意记录保留。

优点是小程序内体验稳定、实现边界清晰、可以保留完整的历史版本记录；代价是协议更新需要发布小程序版本。

### 方案 B：仅前端勾选

协议页面和勾选状态只在小程序内处理，服务端不接收版本和同意记录。实现成本最低，但无法在服务端验证用户是否真正同意，也无法形成可靠的历史版本证据，不采用。

### 方案 C：远程协议中心

由后端返回协议正文、版本和发布日期，小程序动态渲染并记录同意。更新灵活，但需要新增协议发布、缓存、回滚和管理能力，超出当前登录页改造范围。

## 用户流程

### 登录页

登录页在表单底部展示一个明确的未选中复选框和协议链接：

> 我已阅读并同意《用户服务协议》和《隐私政策》

协议名称可独立点击打开对应页面，点击协议链接不改变勾选状态。页面返回后保留用户当前填写内容和勾选状态。

以下操作在未勾选时统一拦截，并提示“请先阅读并同意《用户服务协议》和《隐私政策》”：

- 获取短信验证码；
- 手机号验证码登录；
- 微信手机号快捷登录；
- 发起微信或 QQ 第三方登录；
- 第三方登录后的手机号绑定完成动作。

勾选状态只作为当前登录流程的前置确认，不使用本地永久记忆替代服务端同意记录。用户重新登录、协议版本变化或清除小程序数据后，应重新确认。

### 协议页面

两个协议页面使用同一套阅读壳层：顶部返回、协议名称、版本号、更新时间、分节标题和正文。正文支持纵向滚动，不提供“同意”按钮，用户在登录页完成同意动作。

协议页面文案使用清晰的中文段落，重要的责任限制、敏感个人信息、第三方处理、未成年人、争议解决和协议变更内容单独成节，不使用小字号或低对比度隐藏。

## 协议内容范围

### 《用户服务协议》

协议初稿包含以下章节：

1. 协议的接受、主体和适用范围；
2. 点餐、堂食、自取、配送和账户服务说明；
3. 注册、登录、账户安全和身份使用；
4. 商品信息、价格、订单成立、支付和电子凭证；
5. 取消、退款、缺货、配送异常和售后处理；
6. 用户发布内容和文明使用要求；
7. 知识产权和品牌内容使用；
8. 服务中断、不可抗力和责任边界；
9. 未成年人使用要求；
10. 协议变更、服务终止和账户注销；
11. 适用法律、争议解决和联系渠道。

涉及价格、库存、配送范围、退款时限等经营信息的条款只引用实际页面规则，不虚构当前项目尚未确定的承诺。

### 《隐私政策》

隐私政策初稿包含以下章节：

1. 个人信息处理者身份和适用范围；
2. 收集的信息、处理目的、使用场景和必要性；
3. 手机号、微信身份、头像昵称、收货地址、订单信息、设备与日志信息的分类说明；
4. 敏感个人信息提示、最小必要原则和拒绝后的影响；
5. 微信、短信、支付、云服务等第三方或受托处理方说明；
6. 信息存储地点、保存期限和删除机制；
7. 查阅、复制、更正、删除、撤回同意、注销账户等用户权利；
8. 信息安全措施和安全事件处置；
9. 未成年人个人信息保护；
10. 隐私政策更新、版本记录和联系方式。

隐私政策不得把“同意协议”扩大为同意所有营销或非必要信息处理。营销通知、个性化推荐等如未来新增，应设计独立选择和撤回入口。

## 协议版本

小程序和服务端共享以下稳定标识：

```ts
type LegalDocumentType = "USER_AGREEMENT" | "PRIVACY_POLICY";

const LEGAL_DOCUMENT_VERSIONS = {
  USER_AGREEMENT: "2026-08-17",
  PRIVACY_POLICY: "2026-08-17",
} as const;
```

正文、发布日期、版本号和主体配置集中维护，登录请求只提交版本标识，不提交整篇协议正文。服务端拒绝缺失、未知或已失效的用户协议版本，并返回可识别的错误信息，提示用户更新小程序后重试。

管理员或商家账号使用独立的后台/商家登录流程，不被消费者协议确认逻辑误伤；只有 `audience=user-api` 的用户登录要求协议版本。

## 服务端数据与接口

### 数据模型

新增 `UserLegalConsent` 模型：

- `id`：主键；
- `userId`：用户；
- `documentType`：`USER_AGREEMENT` 或 `PRIVACY_POLICY`；
- `version`：已同意的协议版本；
- `acceptedAt`：同意时间；
- `ip`：请求 IP，可为空；
- `device`：设备标识，可为空；
- 唯一约束：`userId + documentType + version`；
- 索引：`userId + acceptedAt`。

每次用户确认新的协议版本都新增记录，不覆盖旧版本。已有用户在下一次用户登录时确认新版本。

### 请求契约

用户登录相关请求新增：

```ts
type LegalConsentInput = {
  userAgreementVersion: string;
  privacyPolicyVersion: string;
};
```

以下 `user-api` 请求携带并校验该对象：

- 手机号登录；
- 微信小程序手机号登录；
- 第三方登录后的手机号绑定。

服务端在完成用户身份解析后写入两条同意记录，并在认证审计元数据中保留协议版本和登录方式。登录失败时不写入同意记录。

验证码发送仍由小程序前端在未勾选时拦截；服务端不要求验证码发送阶段具备用户 ID，避免为了发送验证码提前创建账户或同意记录。

## 登录页视觉调整

- 背景保持浅暖灰，内容组上移并减少顶部空白；
- 标题减小字重和字号，副标题保持清晰但降低对比度；
- 表单卡片使用更轻的边框/阴影和较小内边距；
- 微信快捷登录改为浅色辅助按钮或品牌中性按钮，避免绿色与品牌红形成冲突；
- 登录按钮继续使用品牌红，验证码按钮使用浅红底；
- 输入框、验证码按钮和主按钮统一圆角与高度；
- 协议确认放在主按钮之前，字号保持可读，链接使用品牌红并有足够点击区域；
- 取消第三方登录入口的视觉抢占，但不删除已有能力；
- 不修改登录脚本中的认证调用、倒计时和错误文案映射，只增加同意前置检查和协议跳转。

## 测试与验收

### 自动化测试

- 协议版本常量包含两份文档；
- 两个协议页面包含标题、版本、更新时间和所有必需章节；
- 未勾选时四类登录动作不会发起请求；
- 勾选后请求携带两份协议版本；
- 服务端拒绝缺失或错误版本；
- 服务端对新用户和已有用户各写入两条同意记录；
- 重复同意同一版本不产生重复记录；
- 管理员和商家登录不要求消费者协议版本；
- 微信小程序编译通过，协议页面可打开、返回和滚动。

### 手工验收

1. 首次进入登录页，复选框未选中，所有登录相关操作均被拦截。
2. 点击两份协议可分别打开，返回后输入的手机号、验证码和勾选状态仍在。
3. 勾选后，短信登录和微信手机号快捷登录都能继续。
4. 修改协议版本后，旧客户端登录收到更新提示；更新小程序后重新确认即可登录。
5. 协议正文在常见手机高度和微信开发者工具中可完整滚动阅读。
6. 正式发布前补齐运营主体、联系地址、客服邮箱/电话、投诉渠道、实际短信/支付/云服务商和真实保存期限，并完成法务审核。

## 待补运营信息

以下内容不能由代码合理推断，先以配置占位，发布前必须由运营方提供：

- 运营主体全称、统一社会信用代码和注册地址；
- 客服电话、客服邮箱、个人信息保护负责人或联系渠道；
- 用户投诉、退款和争议处理入口；
- 实际短信服务商、支付服务商、云服务商及其处理范围；
- 订单、支付、地址、日志等数据的真实保存期限和删除规则；
- 实际配送范围、退款规则、未成年人使用规则和适用争议解决机构。

## 依据与边界

协议结构参考《中华人民共和国个人信息保护法》关于合法、正当、必要、透明、敏感个人信息、个人权利和个人信息处理者义务的要求；参考《中华人民共和国消费者权益保护法》关于经营者与消费者公平、诚信交易及消费者知情权的要求；参考《中华人民共和国民法典》关于电子数据书面形式和格式条款提示说明义务的要求。
