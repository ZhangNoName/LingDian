# LingDian 模块目录与实现状态

> 审查基线：2026-08-29 当前工作区。本文是代码现状目录，不是目标功能承诺。系统关系见 [系统结构](./11-system-structure.md)，上线缺口与权限方案见 [权限与缺口分析](./13-permission-and-gap-analysis.md)。

## 1. 状态口径

| 状态 | 定义 | 是否可对外宣称可用 |
| --- | --- | --- |
| **已实现** | 主流程、权限、异常处理和基本测试均存在 | 可以，但仍须经过目标环境验收 |
| **部分实现** | 存在真实 API/数据链路，但关键分支或运营能力未闭环 | 只能说明已完成的子能力 |
| **占位** | 页面、字段或接口壳存在，主要数据仍是静态值/mock | 不可以 |
| **缺失** | 仓库中没有可执行主流程 | 不可以 |

成熟度不是按“有页面”或“有数据表”判断，而是同时检查：入口、服务端规则、权限与数据范围、持久化、异常补偿、审计、测试和运营处置。

## 3. 客户端模块

### 3.1 `admin/`：平台管理端

平台端当前应定位为“账号与日志治理端”，不是完整的平台运营后台。

| 页面/模块 | 状态 | 真实能力 | 权限 | 缺口 |

| 登录、刷新、退出、强制改密 | 已实现 | 管理员密码登录、刷新会话、临时密码强改 | `admin-api` audience | 客户端接收登录结果时还应显式校验 audience/角色 |

## 4. 后端领域模块

### 4.1 `auth`：身份、会话与身份提供方 — 部分实现

**职责**

- 顾客手机号/微信/QQ 登录与绑定；
- 商家、管理员密码登录、忘记密码、强制改密；
- access/refresh session、audience 隔离、账号状态和 `sessionVersion`；
- 协议版本与同意记录、认证审计。

**已实现的关键约束**

- 三类 audience：`user-api`、`merchant-api`、`admin-api`；
- 受保护请求同时校验 JWT 与数据库 session；
- 密码、角色、账号状态或门店范围变化可撤销既有会话；
- refresh token 使用 cookie/受控客户端流程，不写入普通业务响应字段。

**主要缺口**

- 同设备退出后重新登录会复用原 session 标识，存在旧 access token 在有效期内重新生效的风险；
- 顾客自助注销/删除、身份解绑、设备/会话管理和认证数据清理策略缺失；
- 验证码、OAuth 临时态、session、审计等缺独立生命周期任务；
- 商家只存在单一 `MERCHANT` 角色，没有员工与岗位权限。

代码入口：`backend/src/modules/auth/`、`backend/src/common/auth/`。

### 4.2 `admin-users`：平台账号治理 — 部分实现

提供统一账号列表、创建/编辑、启停、密码重置、角色与商家门店范围维护。服务端具备“不能管理自己、不能管理同级或更高等级”等层级策略。

缺口是策略仍绑定固定角色枚举，且 `admin/merchants` 与 `admin/users` 存在职责重叠；没有角色定义、权限点、资源范围授权、审批与授权变更审计。

代码入口：`backend/src/modules/admin-users/`。

### 4.3 `stores` 与 `merchant`：唯一门店与商家范围 — 部分实现

当前能读取公开“当前门店”和商家被授权门店列表。商家门店范围来自服务端签发的 `merchantStoreIds`，并再次由单店 resolver 收口，不能只靠前端传入 store ID。

产品明确只运营一个店铺，因此不建设 Organization/Brand、选店和跨店管理。当前已经把单店模式实现成运行时不变量：

- `STORE_MODE=single` 与 `PRIMARY_STORE_ID` 在生产必填，当前构建对 `multi` fail closed；
- 启动和 `/health/ready` 精确校验主门店存在，营业关闭不等于服务宕机；
- 顾客菜单和下单由服务端注入该门店，错误候选门店在查库前拒绝；
- 商品、订单、支付账户、集成和商家账号分配都限定主门店；
- 商家端只提供真实“门店设置”读取，不提供创建/切换；
- `stores` controller 不直接访问 Prisma，空库读请求不再创建演示门店。

仍缺门店资料、营业时段、服务方式和配送范围编辑及审计；桌台/二维码仅在堂食场景建设。

代码入口：`backend/src/modules/stores/`、`backend/src/modules/merchant/`。

### 4.4 `products` 与 `menu`：商品、SKU、选择组与公开菜单 — 部分实现

**已实现**

- 分类、商品、SKU 基础模型；
- 选择组、选项、SKU 与组/选项绑定；
- 平台商品 CRUD/图片接口；
- 商家商品查询、价格库存与规格配置；
- 公开菜单读取与服务端短时缓存。

**缺口**

- 商家端没有完成从分类到商品发布的建档入口；
- 消费者端只使用默认 SKU，选择组语义与后端不一致；
- `products.service.ts` 混合查询、命令、配置同步、校验和缓存，边界过大；
- 缺乐观锁/版本冲突处理、菜单发布版本和缓存主动失效；
- 平台商品接口是宽 `ADMIN` 角色授权，未按动作权限拆分。

代码入口：`backend/src/modules/products/`、`backend/src/modules/menu/`。

### 4.5 购物车与定价 — 占位/缺失

购物车只存在于顾客端内存；服务端没有购物车、报价或促销计算模块。订单创建时会重新计算 SKU 与选项金额，这是正确的安全底线，但还不能替代可复用的报价能力。

目标模块应负责：跨端可验证购物车、门店隔离、商品可售性、服务方式、原价/优惠/配送费/税费试算、报价有效期与价格快照。`couponCode` 当前被 DTO 接收但没有参与计算。

### 4.6 `addresses`：顾客地址 — 部分实现

按当前用户隔离地址，支持列表、默认、微信导入与删除；下单时会验证地址归属并写入订单快照。

缺口：手工新增/编辑、配送范围校验、地址删除与历史订单快照的数据权利规则。

代码入口：`backend/src/modules/addresses/`。

### 4.7 `orders`：订单与状态机 — 部分实现

**已实现**

- 顾客幂等创建订单；
- 服务端校验门店、商品、SKU、选择组、数量、地址并以整数分计算金额；
- 订单、明细、选项快照、状态日志和 outbox 同事务写入；
- 顾客按本人、商家按授权门店查询；
- 商家/平台状态流转使用服务端状态机。

**缺口与边界问题**

- 没有库存检查、预占、确认或释放；
- 没有客户取消、未支付超时、自动关单；
- 没有接单、备餐、桌台/取餐号、核销、配送等独立履约状态；
- 门店的堂食/外带/自取开关没有在创建订单时作为服务端规则执行；
- 在线订单能被运营动作直接推进到 `REFUNDED`，没有真实资金退款作为前置事实；
- `order.created` 在付款前就可能发给 POS/打印系统，需要明确“预订单”语义或调整事件时机。

代码入口：`backend/src/modules/orders/`。

### 4.8 `payments`：支付意图、资金流水与回调 — 部分实现，当前不可上线

当前工作区正在建设：支付账户、PaymentIntent、PaymentTransaction、WebhookEvent，按订单门店和渠道选择账户，通过 Connector 调用厂商，并验证 HMAC、金额、币种、账户及事件幂等。

现阶段存在四类阻塞问题：

1. 幂等命中发生在订单归属校验之前，可能跨用户返回既有支付意图；
2. 同一订单用不同幂等键可以并发创建多个活动意图，存在重复扣款风险；
3. Connector 同步返回成功时只推进支付意图，订单未必推进到 `PAID`；之后 webhook 可能因意图已成功而提前返回，导致订单永久停留待支付；
4. 顾客端完全没有接入创建意图、厂商 SDK 和结果确认。

此外，订单支付占位的条件更新没有检查是否成功，订单取消与发起支付存在竞态；在途意图引用可原地修改的收款账户，密钥/账户轮换会影响旧回调；仍缺退款意图/流水、主动查单补偿、超时关闭、日终对账、差错/争议工单和生产厂商验收。支付状态只能由支付域驱动订单，订单状态按钮不能代替资金事实。

代码入口：`backend/src/modules/payments/`、`packages/contracts/src/payment.ts`、`packages/db/prisma/migrations/20260829_payment_transactions/`。详细设计见 [支付交易与订单模块设计](./10-payment-order-architecture.md)。

### 4.9 履约与售后 — 缺失

当前订单状态字段承担了一部分“制作中/完成/退款中”展示，但没有独立履约单或售后单。目标至少包括：

- 商家接单/拒单、制作、出餐、叫号、核销；
- 堂食桌台、外带取餐号、配送任务；
- 顾客取消/退款申请、商家审核、支付退款和异常人工处置；
- 打印、设备或第三方履约结果回传。

### 4.10 库存、仓库与采购 — 占位/缺失

数据库只有 SKU 库存数量，商家可以手工改数，顾客页面还明确提示库存暂不阻断。没有库存流水、预占、释放、盘点、仓库、采购、供应商或成本核算。

若首期不做库存阻断，应在产品和合同中明确“展示库存，不保证强一致”；若承诺限量售卖，则库存预占是上线阻塞项。

### 4.11 会员、营销与顾客运营 — 占位/缺失

顾客端会员资产、商家端会员/营销页面都是占位，后端没有积分账户、券、余额、活动、规则或会员等级模块。建议先选择一个最小闭环（例如领券—试算—核销—退款返券），在完成前隐藏生产导航中的模拟数据。

### 4.12 财务、退款、对账与结算 — 占位/缺失

支付意图与交易流水只是资金入口底座，不等同于财务模块。当前缺：退款账、主动查单、渠道账单导入、日终对账、差错处置、商户结算、手续费、发票、财务导出和财务岗位权限。

### 4.13 `integrations`：连接器与可靠投递 — 部分实现

**已实现**

- 部署级与门店级能力/开关；
- 与订单同事务写出 `integration_outbox`；
- 原子认领、重试、指数退避和死信；
- 稳定事件与独立 Connector 的 HMAC 边界。

**缺口**

- 只有 `order.created`；支付、接单、取消、备餐、配送、打印结果等事件未覆盖；
- 缺 inbox/入站幂等与双向状态同步；
- 缺死信查询、重放、跳过和告警界面；
- worker 跟随 API 进程，缺少多副本运行、任务可观测性和独立扩缩容约束；
- outbox 可能包含个人信息，尚未定义最小字段与留存期限。

代码入口：`backend/src/modules/integrations/`、`docs/08-integration-architecture.md`。

### 4.14 `system-log`、认证审计与可观测性 — 部分实现

系统支持客户端错误上送、来源/audience 校验、字段脱敏、分页查询和 30 天错误日志清理；认证模块有独立认证审计，订单有状态日志。

但三类记录彼此分散，商品、价格、库存、集成开关、支付账户等敏感变更没有统一业务审计。数据库虽然有 request/correlation 字段，HTTP 请求没有完整串联；也没有服务指标、分布式追踪、SLO、告警和后台任务面板。

代码入口：`backend/src/modules/system-log/`、`packages/observability/`。

### 4.15 `health` 与后台任务 — 部分实现

`GET /api/health` 可用于进程 liveness，但不检查数据库、迁移、磁盘、Connector 等依赖。outbox 与清理任务运行在 API 内，订单超时、支付查单/对账、数据生命周期任务缺失。

目标应区分：

- liveness：事件循环和进程可响应；
- readiness：数据库、迁移、必需配置、磁盘/对象存储可用；
- dependency health：Connector/厂商可按降级策略使用；
- job health：最后成功时间、积压、失败和死信可观察。

## 5. 页面—API—权限映射摘要

| 调用方 | API 范围 | 后端模块 | 认证/范围 | 当前一致性 |
| --- | --- | --- | --- | --- |
| admin 账号 | `/admin/users*` | admin-users | `AdminGuard` + 账号层级 | 服务端安全；前端动作提示不完全一致 |
| admin 日志 | `/admin/system-logs*` | system-log | `SuperAdminGuard` | 一致 |
| web 商品 | `/merchant/products*`、`/merchant/sku/*` | products | `MerchantGuard` + JWT 门店范围 | 基本一致；无动作权限 |
| web 订单 | `/merchant/orders*` | orders | `MerchantGuard` + JWT 门店范围 | 基本一致；前后端复制状态机 |
| web 集成 | `/merchant/stores/:id/integrations` | integrations | `MerchantGuard` + JWT 门店范围 | 一致；无运营能力 |
| uniapp 菜单 | `/menu/current` | menu/products | 公开 | 数据可读；唯一生产门店解析不确定且 GET 有写入副作用 |
| uniapp 地址 | `/addresses*` | addresses | `UserApiGuard` + 用户归属 | 服务端一致；客户端导航保护有遗漏 |
| uniapp 订单 | `/order/create`、`/customer/orders*` | orders | `UserApiGuard` + 用户归属 | 主体一致 |
| uniapp 支付 | `/customer/orders/:id/payments` | payments | `UserApiGuard` + 应有订单归属 | 客户端未调用；服务端幂等路径有越权缺陷 |
| 平台商品/订单 | `/categories*`、`/products*`、`/orders*` | products/orders | `AdminGuard` | API 存在但无页面；宽角色授权 |
| 支付账户 | `/payment-accounts*`、`/merchant/payment-accounts` | payments | 超管写、商家范围读 | 无平台/商家页面 |

## 6. 共享包与跨层契约

| 包 | 职责 | 当前问题 |
| --- | --- | --- |
| `packages/contracts` | 订单、支付、外部事件等稳定契约 | web 仍复制部分订单类型；支付渠道在 DTO/页面/契约间存在漂移 |
| `packages/db` | Prisma client、schema 与迁移 | 迁移历史缺业务核心表的初始基线，空库不能仅靠现有迁移可靠重建 |
| `packages/observability` | 三端客户端错误捕获和上送 | 只覆盖错误上报，不含 trace/metric 或业务审计 |
| `packages/icons` | 图标统一导出 | 边界清晰 |
| `common` | 响应码与轻量通用能力 | 应继续避免放入领域状态和数据库模型 |
| `theme` | 管理端/顾客端设计令牌 | 需持续校验组件是否绕过令牌直接硬编码 |

契约治理要求：金额字段必须说明单位；枚举只能在共享契约定义一次；变更需兼容策略；前端 ViewModel 可扩展展示字段，但不能重新定义资金、状态或权限事实。

## 8. 模块文档完成定义

后续每个领域模块独立成文时，至少包含：

1. 状态、负责人、目标版本和 feature flag；
2. 职责、非职责与依赖方向；
3. 实体、状态机、金额/时间单位和业务不变量；
4. 三端页面、路由、组件与真实/模拟数据标识；
5. API、事件、共享 contract 和数据库所有权；
6. audience、角色、动作权限、门店/用户数据范围；
7. 正常、异常、超时、重试、补偿与人工处置流程；
8. 幂等、并发、审计、PII、留存与删除规则；
9. 单元、集成、契约、E2E、压测和验收条件；
10. 已知缺口、风险、监控指标与回滚方案。

生产导航中的模块必须达到“已实现”，或受关闭状态的 feature flag 控制；“占位”页面不得显示看似真实的交易、库存、会员或财务数据。
