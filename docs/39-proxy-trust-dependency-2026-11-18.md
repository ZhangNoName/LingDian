# 代理地址依赖补丁 · 2026-11-18

## 审查结论

趋势交付时重新查询生产依赖公告，发现 `proxy-addr@2.0.7` 经 Nest/Express 进入 API 运行时，另有工具链路径。上游 [GHSA-jqcg-44mw-7w3h](https://github.com/advisories/GHSA-jqcg-44mw-7w3h) 的触发前提是配置特定 IPv4-mapped IPv6/短前缀信任网段，可能错误信任外部 IPv4，从而影响依赖 `req.ip` 的限流/审计。官方 [2.0.8 变更记录](https://github.com/jshttp/proxy-addr/blob/master/HISTORY.md) 提供修复。

当前 API 在生产环境校验 `TRUST_PROXY_HOPS=1`，本地缺省为 loopback，并未配置公告所述的错误网段。因此依赖扫描的 critical 分级不代表已证明当前部署存在同样的可利用链；仍更新运行时补丁，避免继续使用带已知缺陷的地址判断实现。

## 变更

工作区 overrides 将 `proxy-addr@>=2 <2.0.8` 限定到 2.0.8，锁文件中 Express 4/5 均解析至该版本；没有更新其他依赖、增加另一份测试专用 Express 或改变现有代理层数。现有认证、门店隔离、库存和界面流程不变，无数据库迁移或环境变更。

新增测试通过 Nest 当前实际使用的 Express 解析 proxy-addr：

- 特定短 IPv6/映射网段不能把无关 IPv4 当可信代理，正确的映射网段仍正确匹配；loopback 保留本地映射识别并拒绝外部地址。
- 在真实本机 HTTP 请求中，一层代理模式只采用转发链最近的客户端地址，不采纳更早一层注入地址。
- 禁用代理信任时忽略转发头，继续使用 socket 地址。

本轮不把通用 IPv6 缺陷描述为当前一层代理模式的复现，也不通过扩大代理信任范围来消除告警。网络拓扑与现有 Nginx/一层代理约定继续由部署配置保障。

## 验证与后续

针对性 3 项测试通过；用安装缓存中的旧 2.0.7 单独复核同一短映射网段，确实将合成外部 IPv4 判为可信，而升级后的测试返回 false；重新执行生产依赖审计后，proxy-addr 公告消失，critical 从 1 降为 0。整体仍有 121 项（52 high / 57 moderate / 12 low），审计继续非零；上传、图像、数据库驱动、其他运行时及工具链依赖需要继续按实际调用路径和兼容版本处理，不能扩张旧的 DCloud 风险例外或宣称依赖已清零。

本轮仅修复此依赖补丁，未修改业务数据库、环境文件或部署运行状态。发布需重新安装锁定依赖并重建/发布使用它的运行镜像，旧运行镜像不会因仓库锁文件变化自动生效。

补丁后全仓类型检查、构建和 `pnpm test` 均通过：778 项通过，1 项因缺少 Docker Compose v2 跳过（API 373）；源码质量、文档链接、迁移和部署路由 18 项检查通过。构建保留既有上游 PURE 注解等非阻断提示。
