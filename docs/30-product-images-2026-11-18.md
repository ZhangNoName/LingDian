# 商家商品图片维护 · 2026-11-18

## 使用流程

商品管理增加“商品图片”分区。先保存商品草稿，再选择 JPEG、PNG 或 WebP（最多 3 MB），预览后“上传并保存”；已有图片可替换或确认移除。保存直接更新当前商品图片，不合并进规格/价格表单，也不隐式改变商品发布状态。图片不改写 SKU、配方、库存、价格和已下单记录。

选择图片后，其他分区与发布动作禁用，用户先上传或明确放弃；保存期间禁用关闭与重复操作。版本冲突、网络错误保留文件与预览；响应丢失用同一文件、请求键与版本重试，不重复改商品。重新读取前明确确认放弃选择，并保留图片分区。商品管理各分区统一增加未保存关闭确认。

无图、读取失败、格式/大小错误、缺少版本、保存成功及移除均有中英文反馈。手机用缩略图和原生文件选择，上传按钮可直接看到；对象 URL 在取消、保存和组件销毁时释放。重新选择无效文件会清除此前的待上传选择，避免误上传上一张图片。创建/替换成功的图片在列表详情和顾客菜单继续复用 Product.imageUrl。

## 上传和文件归属

新接口位于授权门店和商品路径下，AccessTokenGuard / MerchantGuard 后增加商品范围 Guard，在 Multipart 文件读取前校验当前用户、门店和商品归属。服务层再次验证范围；请求体只接收 requestId 与 expected_version，不能直接声明 imageUrl 或其他门店。

文件先在受限内存中接收，严格限制大小、文件/字段数量。Sharp 校验真实编码与声明 MIME、拒绝非静态 JPEG/PNG/WebP、限制 4,000 万输入像素，按方向旋转并缩至最长 960 像素，编码 WebP 且不带原始元数据。原始文件不落盘，不使用客户端文件名形成存储路径，不通过远程 URL 取图。

商家文件写入现有 uploads/products/merchant 下的店内哈希目录，以服务端 UUID 命名。先写完整临时文件，再以不覆盖的链接发布固定路径；同一请求并发重试不能覆盖已发布字节。只在文件就绪后提交数据库关联。该目录位于既有持久化 uploads 挂载和备份中，无新的外部存储账号要求；多实例若扩展至不同主机，需要另行配置共享存储或对象存储。

商品图片是顾客菜单的公开资源，不是私有附件。替换/移除只更新当前商品引用，旧已提交文件与请求记录保留；已公开 URL 与缓存仍可能访问，不把移除描述为撤销旧链接。

## 版本、重试与清理

ProductImageRequest 按 storeId/requestId 唯一，指纹包含 actor、商品、操作、期望版本、MIME 和原文件 SHA-256，产品关联使用门店复合外键。请求先持久化 PENDING 归属，再落文件；在一次 ReadCommitted 事务中认领请求、认领商品版本、更新 imageUrl、写审计并标记 APPLIED。竞争请求读取已提交结果；不同内容复用请求键拒绝。已提交请求重放返回当前商品，不将旧图片再次覆盖到新版本。

已知旧版本或存储失败会关闭该尝试并尽力清理其文件。数据库/审计异常保留有归属的 PENDING 文件，允许相同请求重试；即使进程在文件写入和提交之间退出，也有持久化尝试记录可回收。PENDING 超过 24 小时不再接受重试。API 启动及每小时执行一批最多 100 条的清理，关闭过期尝试、删除失败/过期文件和对应临时文件后标记 CLEANED；已提交文件不参与清理。任何被商品引用的候选文件保留为 RETAINED。周期日志不输出图片内容。

文件系统与数据库不是同一事务资源：先落文件及持久化归属、再提交引用，借助重试和过期回收收敛未完成尝试；不宣称跨资源 ACID。文件存储故障、旧版本、审计失败都不会部分修改商品、SKU、配方或库存。

## 部署

新增 `20261118_zz_product_images`：product_image_requests、products(id,storeId) 唯一索引和门店复合关联。无旧图片迁移或删除；旧平台通用图片接口保留兼容，商家使用新受控路径。通过安全迁移入口应用后重新生成 Prisma Client，再发布 API/Web。

新增三个前端 HTTPS 域名的 /uploads/products/ → API 代理，开发 Web 也代理该路径；否则相对图片 URL 会被 SPA 接走。完整发布需安装并校验更新后的 Nginx 模板，保留原 API、metrics 保护及 uploads 持久化/备份。静态文件沿用既有 ETag 和不可变缓存策略。
