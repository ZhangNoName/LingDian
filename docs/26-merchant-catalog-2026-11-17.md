# 商家商品建档与菜单发布 · 2026-11-17

## 产品流程

商品页增加“新建商品”，在当前授权门店选择/新建分类，填写名称、说明、初始规格/价格和推荐设置后保存为草稿。随后复用商品管理弹窗配置规格、顾客选项和销售配方，再单独确认发布。没有把建档保存与发布合成一次隐式操作。

- 基本资料、规格/价格、顾客选项分区维护。基本资料保存不改写 SKU、价格、库存或已有配方；价格和规格仍通过既有配置接口保存。
- 新建分类按门店查找/复用同名可见分类；商家并发创建同名分类会串行返回同一记录。分类查找每次最多 50 条，选中的分类在后续查找后仍保留。隐藏分类可在已有资料中辨认，发布前必须选择可见分类。
- 草稿、已发布、售罄和归档使用清晰状态及动作。已归档商品先恢复草稿；发布、下架、售罄和归档先展示目标状态与影响，再由用户确认。
- 发布提示核对名称、售价、规格和必选项，并说明未配置配方的规格不提供自动原料限量承诺。状态只影响后续菜单/下单，已下单快照不变；下架和归档保留规格与配方。
- 未保存的规格/选项会阻止切到资料页及发布；未保存的资料会阻止切到规格/选项及发布。用户先保存或明确放弃，避免误以为正在发布尚未保存的新价格/名称。配置分区之间仍保留同一草稿。
- 保存、分类创建和状态变更期间禁用重复操作与关闭；失败保留表单。中英文与手机布局共用全局语言设置和现有 Dialog/表单，没有新增 UI 库。

图片维护仍通过平台管理。商家暂不提供图片上传、分类重排/改名/隐藏、批量导入或独立菜单版本发布，本轮界面明确保留这些边界。

## 身份、版本和数据一致性

新增当前商家门店路径下的分类列表/创建、商品草稿创建、资料和状态接口；每个方法先检查 signed merchant/store scope，查询和写入继续以当前门店限定对象。请求体不接收 storeId、创建状态或参考库存等额外字段，继承全局 DTO 白名单拒绝策略。

草稿创建保存店内唯一 requestId、规范化请求 SHA-256（含当前用户）及 DRAFT 状态；同一请求重复/并发提交只创建一件商品和一个初始活动默认 SKU，不同内容复用请求键拒绝。没有配方、初始原料库存或订单预占被自动生成。分类创建锁定当前门店行后查找/创建，复用不改写隐藏状态；平台旧分类接口仍可能产生旧重名记录。

资料/状态更新沿用 configurationVersion，在事务认领版本后读取最新状态。审计与业务写入在同一事务提交/回滚。越权分类/商品、旧版本和不支持的状态转换拒绝，校验失败不消耗版本。缓存统计在成功写入后失效。

发布检查当前分类归属/可见性、活动规格，以及顾客默认活动规格会显示的已启用必选组：引用选项须有活动规格、同店且商品已发布（当前商品自身引用按本次发布后的状态判断）。缺少足够可用选项时拒绝发布。之后依赖商品仍可被其他操作下架，顾客下单继续以现有服务端校验为准；本轮不承诺依赖配置永久可用。

平台旧宽角色接口仍保持兼容，不自动扩大为商家权限；旧平台写入递增配置版本，使商家旧草稿失效。

## 迁移与验证

新增 `20261117_z_merchant_catalog`：可空 creationRequestId/creationFingerprint、店内唯一创建请求索引，以及 Product.description 从原 varchar 扩为 TEXT，接口最多 2,000 字。旧商品请求键保持 NULL，不补造创建来源；既有名称、SKU 和描述保留。先通过安全迁移入口部署，再同步更新 API/Web。

- 临时 MySQL 8.4.13 完整重放 20 个迁移并通过历史/schema 无漂移校验。
- 生产服务验证同名分类并发、创建请求重放、长说明、分类/商品门店隔离、草稿/发布/售罄/归档/恢复及菜单可见性、资料/状态旧版本拒绝、缓存失效、审计失败回滚、SKU/配方保留，以及隐藏分类/无活动规格/不可用必选项拒绝。
- 单元测试验证 DTO 名称/金额/长度、拒绝注入范围/创建状态、先验 scope、状态转换和未知状态保守处理；前端请求验证路径编码、请求键、版本与分类查询。
- 浏览器以双店合成 API 数据验证分类和草稿创建、响应丢失重试、未保存保护、状态确认/取消/保存锁、资料冲突保留、分类选择保留、英文手机界面及切店清理。浏览器验证不调用业务库或发布真实菜单。

全仓 `pnpm test` 共 720 项通过，1 项因本机缺少 Docker Compose v2 跳过；`pnpm run type-check`、`pnpm run build` 均通过。最后的手机取消入口调整后，Web 115 项测试、Web 类型检查以及两组浏览器回归再次通过；源码质量、文档链接和迁移完整性 8 项检查通过。构建仍有既有依赖的 PURE 注解提示。

实际 MySQL 额外验证：资料读取后、认领版本前若发生并发发布，资料更新必须依据锁定后的最新 ACTIVE 状态校验分类，不能借旧草稿状态移入隐藏分类。临时数据库与前端验证进程在提交前关闭并清理，未修改业务库、环境文件或全局服务。
